# Правила проекта «Заказы»

- Разрабатывать по docs/TZ_Orders_Prototype_v1.md с уточнениями пользователя. Изменения 0.4: docs/GROUP_FULFILLMENT_0.4.md; прежний контур доставки: docs/DELIVERY_AND_UI_0.2.md.
- Android Kotlin + Compose + MVVM + Room; локальная работа, без собственного сервера.
- Репозиторий оставлять Public по прямому решению Дмитрия от 12.11.2026. Исходники разрешено обновлять в текущем репозитории. Базы, пользовательские данные и секреты не публиковать.
- Kimi работает только с вручную переданными архивами. Не поручать ему GitHub, git push/pull/clone, PR, Actions, публикацию артефактов; не выдавать токены. Дмитрий вручную передаёт входной архив Kimi и возвращает result.zip GPT.
- Каждое задание Kimi имеет базовую версию, ограниченный объём, критерии завершения. Результат: полные изменённые файлы, DELETE_LIST.txt, REPORT.md, manifest.json. Не зацикливаться на внешних операциях и повторных проверках; выдать достигнутый результат и блокеры.
- Реальные результаты, проверки и ограничения отражать честно. APK выдавать только после фактической сборки; не заявлять о проверке на телефоне без неё.
- Бизнес-логика независима от UI, Room, почты/MAX. Будущее объединение — через интерфейсы, UUID и версии миграций.
- Денежные вычисления BigDecimal, суммы в копейках/decimal-строках; не Float/Double. Null не равно нулю.
- Расход и передача денег — разные операции. Перенос старого долга не меняет прибыль новой группы повторно.
- Утверждённые финансовые операции не переписывать; исправлять отдельными корректировками/сторно.
- Никаких деструктивных миграций; бэкап и безопасное восстановление входят в 0.1.
- Проверки соответствуют изменениям; не повторять успешные без новой причины. Не расширять объём самовольно.
- Секреты, ключи, реальные переписки/заказы, базы и бэкапы не коммитить и не передавать Kimi.

- Доставка: прогноз не равен счёту. Получения от клиента и оплаты логисту — отдельный журнал, не расходы товара и не взаиморасчёты с посредником.
- Старые записи DELIVERY из 0.1 не интерпретировать автоматически как прогноз/счёт/оплату. Сохранять и явно обозначать для ручной проверки.


## Навыки разработки

- Перед изменением прочитать `.agents/skills/INDEX.md` и `.ai/PROJECT.md`; выбрать только профили по текущей задаче. Не загружать все навыки целиком.
- Для дефекта читать `systematic-debugging`; для изменения архитектуры — `architecture-guardian`; для значимой логики/регрессии — `test-driven-development` и `regression-control`; перед завершением — `verification-before-completion`, перед выпуском — `release-manager`.
- Инструкции навыков дополняют действующие правила этого файла. Соблюдать ограничения среды и текущую задачу пользователя; навык сам по себе не разрешает деплой, внешние отправки, расширение доступа или передачу работы Kimi/другим агентам. При существенном конфликте описать его, не выбирать молча.
- Исправлять подтверждённую первопричину, сохранять принятое рабочее поведение. Не добавлять обходные задержки/сбросы и лишние слои. Существующие API и формат данных менять только по доказанной необходимости в рамках задачи.
- Проверки выбирать по риску и фактическим командам проекта. Не писать формальные тесты для косметики/текста и не повторять успешные прогоны без новых изменений или основания.
- Ключи подписи, токены, пароли, реальные письма, заказы и базы не добавлять в Git и логи. Для Android сохранять действующую подпись; несовместимость подписи не исправлять потерей данных пользователя.
- В рамках порученной реализации действовать до проверенного результата, не переспрашивать обычные технические решения и уже данное разрешение. Не выполнять дополнительные агенты/модели и платные прогоны только потому, что их предлагает сторонняя методика.
- Итог сообщать кратко: результат, фактическая проверка, ссылка, существенный блокер. Полные логи сохранять отдельно без секретов.
