# Контроль регрессий

1. Определить исходный подтверждённый пользователем сценарий, последнюю рабочую версию и изменяемую границу. Из памяти брать ориентир, факты проверять по текущим исходникам и ТЗ.
2. Составить компактную матрицу: действие → ожидаемый результат → способ проверки. Включить исходный дефект и ближайшие связанные функции, а не всё приложение без причины.
3. Для Почты при затрагивании просмотрщика проверить pinch zoom, скрытие панелей, перекрытие текста, якорь прокрутки, раскрытие истории, возврат в список и вложения. MIME/отправку проверять отдельно на обезличенных письмах.
4. Для Заказов при изменении расчётов проверить валюту, курс, доставку, null/ноль, округление, долг и повторное открытие сохранённого заказа; для миграции — обновление старой базы.
5. Для веб-проектов проверять роли, изоляцию организаций, связанные записи и документы; для магазина — карточку, поиск, админку и массовый импорт, если они затронуты.
6. Разделять автоматические тесты, визуальную проверку, фактическую проверку устройства и непроверенные сценарии. Выполненные успешные проверки не повторять без новых оснований.
7. Удалить экспериментальные исправления и диагностику, не участвующие в подтверждённом решении. Не считать удаление диагностических средств доказательством исправления.
