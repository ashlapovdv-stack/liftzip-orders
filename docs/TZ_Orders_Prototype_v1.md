# Техническое задание: Android «Заказы»

Версия ТЗ: 1.0. Дата: 11.11.2026. Заказчик: Дмитрий / Lift-ZIP.
Статус: основа реализации первого рабочего прототипа. Начальный этап — 0.1; последующие этапы не выдавать за готовые функции 0.1.
Репозиторий: https://github.com/ashlapovdv-stack/liftzip-orders. Создан Дмитрием; видимость Private проверена 11.11.2026.

## 1. Цель и принятые решения

Настоящее Android-приложение для проверки удобства на телефоне: создавать оплаченные заказы, собирать расчётные группы, рассчитывать себестоимость и прибыль, искать историю цен. Данные сохраняются локально; без собственного сервера, регистрации и облачной базы. Один пользователь, основное устройство Xiaomi 15. Проект «Заказы» отделён от приложения «Почта» и экспериментальных MAX Integration Test.

Заложить дальнейшее объединение в экосистему Lift-ZIP: независимая бизнес-логика, стабильные идентификаторы, версии схемы, перенос данных. Не обещать объединение без миграционной работы. Разные APK не открывают один SQLite-файл; общий доступ через публичную папку запрещён.

Качество: устранять первопричины; не маскировать ошибки задержками, повторными запусками и ручной очисткой базы. Интерфейс уточняется по использованию на телефоне.

## 2. Работа с Kimi — обязательное правило проекта

Kimi не поручать операции с GitHub: создание репозиториев/веток, clone/pull/push, коммиты, PR, Issues, получение и публикацию артефактов, проверку Actions. Не требовать от пользователя исправлять GitHub-взаимодействие Kimi. Не передавать Kimi GitHub-токены и ключи подписи.

Основной порядок: GPT готовит ограниченное задание и архив исходников → Дмитрий вручную передаёт их Kimi → Kimi выполняет задачу локально и формирует файлы → Дмитрий вручную возвращает архив GPT → GPT проверяет изменения, интегрирует, собирает и выдаёт APK. Репозиторием управляет GPT в пределах доступных полномочий либо Дмитрий. Отсутствие доступа к GitHub не мешает локальной работе Kimi.

Пакет Kimi содержит TASK.md, исходники одной обозначенной версии, manifest.json (базовая версия/идентификатор и SHA-256 входных файлов), только необходимые материалы. В задании точно указаны разрешённые изменения, критерии приёмки, команды проверок и критерий завершения.

Результат: result.zip с полными изменёнными/новыми файлами по относительным путям, списком удалений DELETE_LIST.txt, REPORT.md (что сделано, проверки и фактический результат, ограничения), исходным manifest.json. Не включать build/, кэши, local.properties, секреты, реальные переписки/базы. APK допустима отдельным файлом, если Kimi действительно собрал её; отсутствие SDK не блокирует выдачу исходников. Не считать неподтверждённую сборку успешной.

Завершение Kimi: выполнить приёмочные проверки один раз; повторять только после исправления выявленной ошибки. Не начинать дополнительные аудиты/рефакторинг вне задания. Если внешняя операция или зависимость недоступна, прекратить повторы, описать блокер и сразу выдать доступный результат. Если сформировать архив невозможно — выдать полные изменённые файлы отдельными вложениями и отчёт. Не тратить остаток работы на загрузку в GitHub.

Первая реализация может выполняться GPT без Kimi; порядок выше обязателен при его подключении.

## 3. Технологии и границы модулей

Kotlin, Jetpack Compose, MVVM, Coroutines/Flow, Room поверх SQLite. Денежная математика — BigDecimal; Float/Double для денег, курса и итогов запрещены. Android 8+ (minSdk 26); compile/target SDK и совместимые версии инструментов фиксируются при первой проверенной сборке. Запрещены динамические версии зависимостей. Gradle Wrapper, каталог версий, README с воспроизводимой сборкой.

Минимальные Gradle-модули: :app (Compose, ViewModel, навигация), :core:domain (модели, расчёты, сценарии, интерфейсы репозиториев; без Android/Room), :core:data (Room, реализация репозиториев, миграции, экспорт/импорт). В app отдельные feature-пакеты orders, groups, prices; не создавать десятки пустых модулей ради будущих функций. Состояние UI через ViewModel/StateFlow; база — источник истины, не глобальный изменяемый список.

UI не выполняет SQL и не содержит денежных формул. Изменение финансовых данных — через доменные сценарии и транзакции. SQL/IO вне главного потока. Каталог и история цен не зависят от IMAP или MAX. Будущие интеграции передают DTO со ссылкой на источник; не получают прямого доступа к таблицам.

Плановый applicationId: ru.liftzip.orders; зафиксировать до первого APK, затем не менять. Отдельные debug/release ключи; обновления тестовых APK подписываются одним сохранённым тестовым ключом. Production-ключ не хранить в репозитории или архиве для Kimi.

## 4. Границы первой версии 0.1

Обязательно:
1. Три рабочие вкладки «Заказы», «Группы», «История цен».
2. Создание, просмотр и редактирование оплаченного заказа с несколькими позициями; локальное сохранение.
3. Один справочник товаров с поиском и повторным использованием товара.
4. Ввод продажи, суммы полученной оплаты, закупочной цены/валюты/курса, количества и дополнительных расходов; неизвестные поля допустимы.
5. Предварительная себестоимость и прибыль с явной индикацией неполного расчёта.
6. Автоматическое включение нового заказа в формируемую группу.
7. «Завершить формирование»: закрыть набор и атомарно создать следующую группу. Предыдущую можно рассчитывать дальше.
8. Сводка группы и переход к заказам; поиск товаров и простая история фактических продаж/закупочных расчётов из заказов.
9. Экспорт и восстановление локальной резервной копии, версия схемы и недеструктивные миграции. Не откладывать сохранность вводимых данных до версии 0.5.
10. Проверки денежных формул, инвариантов групп, сохранения, миграций и восстановления; APK и исходники для передачи.

В 0.1 не включать: реальные денежные переводы, учёт взаимозачётов/возвратов, финальное закрытие групп, интеграции почты/MAX/OpenCart, автоматическое чтение писем, языковые модели, сервер/синхронизацию, полный контроль доставки. Не показывать неработающие кнопки этих функций как действующие.

Важно: возможность завершить формирование — не финансовое закрытие. В 0.1 статус «На расчёте» не означает утверждённый расчёт или подтверждённый выкуп.

## 5. Интерфейс для телефона

Светлый, понятный рабочий журнал, крупные зоны нажатия (не менее 48dp), русские подписи, минимум обязательных действий. Нижняя навигация всегда имеет три названные вкладки. Начальная вкладка «История цен» — исходная гипотеза; после первого запуска запоминать выбранную. Поиск и главные действия доступны без глубокого меню. Никаких декоративных кнопок без функции.

### 5.1. Заказы

Список: номер/дата, клиент или менеджер, краткий состав, сумма продажи/оплаты, группа, готовность расчёта. Фильтры «Все», «Нужен расчёт»; финансовые проблемы появляются при реализации корректировок. Поиск по номеру, контрагенту, товару и артикулу. Отображение списков порциями, без загрузки всех подробностей и вложений.

Создание: клиент/менеджер → позиции → полученная оплата → сохранить. Контрагент может быть текстовым именем, без обязательной отдельной CRM. Минимум одна позиция; у товара достаточно названия, артикул необязателен. Количество > 0; цену продажи за единицу и полученную сумму нужно указать явно. Нулевая цена допустима только с осознанным подтверждением; пустая цена не равна нулю. Частично оплаченные заказы в 0.1 не оформляются: показать разницу и предложить исправить ввод, не подгонять оплату автоматически.

Карточка: основное, позиции, закупочный расчёт, расходы, итоги, группа, история изменений. Закупочную цену/курс разрешено заполнить позже. Различать цену за единицу и сумму строки. Добавление нескольких позиций — повторяемая карточка, а не одна длинная текстовая строка. При уходе с несохранёнными изменениями — сохранить/отменить/остаться. Ошибки ввода показывать возле поля, текст не терять при повороте/возврате из фонового режима.

После завершения формирования группы нельзя менять её состав и удалять входящие заказы. До утверждения расчёта можно уточнять закупочные поля. Изменения состава/выручки после закрытия набора в последующих версиях — только явно оформленные операции; не скрытое редактирование.

### 5.2. Группы

Список: номер, этап, количество заказов, сумма продаж, полученная оплата, известные расходы, число неполных расчётов, предварительная прибыль. На экране группы — те же итоги и список заказов. Если расходы неизвестны, итог не маркируется как окончательная прибыль. Отдельное действие «Завершить формирование», с объяснением последствий и подтверждением.

При первом запуске создать одну формируемую группу. После завершения пустую следующую группу показывать сразу. Пустую группу не отправлять на расчёт. Повторное нажатие или повтор после сбоя не создаёт дополнительную группу. В 0.1 доступны только этапы «Формируется»/«На расчёте».

### 5.3. История цен

Поиск по названию, артикулу и сохранённым вариантам обозначений. Карточка товара: название, артикул, последняя известная продажа, последняя закупочная цена с датой и валютой; список записей с количеством и ссылкой на заказ. Предложение, продажа и закупочный расчёт — разные виды записи. Черновой закупочный расчёт не называть фактической оплатой поставщику.

В 0.1 автоматически появляются записи из заказов. В следующей версии добавляется самостоятельная запись предложения клиенту/поставщику без создания оплаченного заказа. Изменение чернового расчёта не порождает ложную вторую продажу: актуальная запись связана с исходной позицией; история правок хранится отдельно.

### 5.4. Настройки и резервные копии

Выбор места экспорта через системный Storage Access Framework. Экспортировать согласованное состояние базы с метаданными, а не копировать открытый SQLite без учёта WAL. Импорт проверить до замены: формат, версия, контрольные суммы, связи. Показать дату/количество записей и что текущие данные будут заменены; до замены создать восстанавливаемую локальную копию. Неверный/повреждённый/более новый неподдерживаемый архив не меняет действующие данные. Восстановление 0.1 — замена, не слияние.

Пакет переносим между установками с сохранением UUID. Экспорт чувствительных данных явно обозначить как незашифрованный, если шифрование не реализовано; не выдавать обычный ZIP за защищённый. Автоматические системные облачные бэкапы по умолчанию отключить. Записывать успешную дату копии только после завершения записи, показывать предупреждение при её отсутствии. Не обещать расписание фоновых копий до реализации.

## 6. Модель данных и инварианты

Все сущности получают стабильный UUID; видимый номер заказа/группы — отдельный уникальный последовательный номер. Даты событий хранить как UTC Instant, бизнес-даты — LocalDate, отображать в зоне устройства. Сохранять createdAt, updatedAt и revision для изменяемых сущностей. Схему Room экспортировать в репозиторий.

| Сущность | Обязательные данные и смысл |
|---|---|
| Product | UUID, название, исходный артикул/нормализованный ключ, бренд необязательно, алиасы; одинаковый артикул сам по себе не доказывает идентичность разных товаров |
| Order | UUID, номер, дата, контрагент, группа, суммы продажи/полученной оплаты RUB, комментарий, состояние расчёта |
| OrderLine | UUID, заказ, товар, снимок названия/артикула на дату заказа, количество, цена продажи за единицу RUB, закупочная цена за единицу/валюта/курс при наличии |
| CostEntry | UUID, позиция либо заказ либо группа (строго один владелец), вид расхода, сумма/валюта/курс, расчётная или подтверждённая, дата, комментарий |
| SettlementGroup | UUID, номер, состояние набора, времена создания/завершения; позднее отдельные состояния расчёта и сверки |
| PriceRecord | UUID, товар, тип события, дата, цена/валюта, количество, ссылка на исходную позицию/источник, статус предварительного расчёта |
| ChangeEvent | UUID, сущность, тип изменения, время, локальный пользователь, было/стало; без паролей и токенов |
| SourceReference, позднее | Тип MAX/почта/ручной, внешний идентификатор в пространстве источника, безопасная ссылка; исходный текст отделён от подтверждённых полей |
| FinancialOperation, позднее | Неизменяемая операция, UUID, idempotencyKey, исходный заказ/позиция/группа, сумма/валюта, RUB-оценка, вид, дата, ссылка на исправляемую операцию |
| SettlementAllocation, позднее | Явное погашение остатка конкретной операции конкретным расчётом; нельзя зачесть один остаток дважды |

Деньги в БД: Long в минимальных единицах для фиксированных денежных сумм; цена единицы/курс/вес/количество при нужной точности — каноническая decimal-строка с точкой. Операции выполняются через BigDecimal, с контролем переполнения при переводе в Long. Значения null означают неизвестно. Не хранить бизнес-поля заказа только внутри JSON; JSON допустим для снимка источника/аудита и переносимого бэкапа.

Связи и внешние ключи обязательны. Индексы: groupId в Order, orderId/productId в OrderLine, productId+date в PriceRecord, normalizedArticle в Product, entityId+date в ChangeEvent. Поиск 0.1 допускает индексируемый префикс и ограниченный поиск по названию; FTS не внедрять без необходимости. Защита от дублирования производных PriceRecord уникальностью связи с исходной позицией и типом.

Уровень БД/транзакции гарантирует ровно одну формируемую группу, уникальные номера, атомарное сохранение заказа/позиций/истории и атомарное завершение формирования с созданием новой группы. Не обеспечивать эти правила только блокировкой кнопки.

## 7. Денежные правила

Базовая валюта сводки — RUB; закупка RUB/CNY. Курс всегда RUB за 1 CNY, положительный, задан явно и сохранён в снимке операции. Автоподстановка сетевого курса не нужна. Изменение курса по умолчанию не меняет прошлые операции.

Для позиции: продажа = количество × цена продажи за единицу. Закупка в RUB = количество × закупочная цена за единицу × сохранённый курс (для RUB курс 1). Округлять итог каждой денежной строки до копеек HALF_UP, затем складывать округлённые строки. Не округлять сначала курс до целых или закупочную единицу до рублей.

Себестоимость заказа = закупки позиций + относящиеся к ним/заказу расходы. Себестоимость группы = сумма себестоимости заказов + расходы уровня группы. Один расход имеет одного владельца и учитывается один раз. В 0.1 групповой расход не распределять скрыто по заказам: прибыль заказа показывать «без групповых расходов», итог группы учитывает их полностью. Автоматическое распределение веса/доставки между позициями — отдельная будущая функция.

Прибыль = продажи − относящиеся к ним расходы, а не «оплата клиента минус передано посреднику». Пока цена/курс/расходы не подтверждены — «предварительная прибыль». Если часть обязательных затрат неизвестна, показывать «расчёт неполный», а не подменять неизвестное нулём. Нулевые известные расходы подтверждаются пользователем. Отрицательная прибыль допустима и явно видна.

Вес, тариф и фактический расход доставки — отдельные поля. В 0.1 допускается ручной расход доставки, без автоматического начисления по тарифу. Не складывать одновременно вес×тариф и тот же ручной расход. Для 0.2 автоматическая доставка должна иметь явный режим «расчёт по тарифу»/«сумма вручную».

## 8. Последующие этапы: финансовый цикл и взаиморасчёты

Порядок пользователя: собрать оплаченные заказы → завершить набор → уточнить и утвердить расчёт → зафиксировать реальную передачу посреднику → вручную отметить уведомления по каждой почтовой теме → получить подтверждения → сверить финансовую часть. После этого требуется вмешательство только при проблемах, возвратах или доплатах. Группа может быть финансово сверена до окончания доставки.

Входящее письмо нельзя автоматически считать доказательством оплаты поставщику. Отдельно хранить «уведомление отправлено», «ответ получен» и «выкуп подтверждён»; последнее — ручное подтверждение с источником, пока семантика писем не проверена.

Состояние набора, утверждение расчёта, факт передачи денег, подтверждения заказов и сверка — отдельные признаки. Отображаемый статус группы выводится из них, а не заменяет их одной строкой.

Утверждённый расчёт неизменяем. Последующая доплата или возврат — отдельная операция с исходной позицией/группой. Исправление ошибочной операции — сторно и новая операция, не удаление истории. Связь с исходной группой сохраняется даже при погашении в следующей.

Взаиморасчёты с посредником: положительный остаток означает «мы должны посреднику», отрицательный — «наш аванс/кредит у посредника». Долг увеличивается от подтверждённых сумм к оплате, уменьшается от зачтённых возвратов и реальных передач. Суммы разных валют напрямую не складывать: нужна явная согласованная RUB-оценка/конверсия или отдельный валютный остаток.

Формула плановой передачи: расходы новой группы к оплате через посредника + непогашенные доплаты прошлых групп − доступные зачтённые возвраты/авансы. Собственные расходы, оплаченные мимо посредника, влияют на прибыль, но не на его задолженность. Отрицательное «к передаче» показывать как остаток аванса, не как отрицательный платёж.

Пример: расходы группы №15 через посредника 200 000 ₽; возврат по №14 5 000 ₽ и доплата по №14 2 000 ₽ → к передаче 197 000 ₽. При продажах №15 250 000 ₽ прибыль №15 до собственных расходов = 50 000 ₽, а не 53 000 ₽. Корректировки относятся к результату исходной группы №14. Их перенос не создаёт повторный доход/расход в №15. Передача 197 000 ₽ погашает соответствующие обязательства ровно один раз.

Возврат от поставщика не тождественен возврату клиенту: две операции, потенциально разные даты/суммы. Отмена позиции не удаляет ни её оплату, ни возвраты. Корректировка может появиться после сверки; первоначальный снимок остаётся, показывается пересчитанный результат и новое открытое расхождение.

## 10. Приёмка 0.1

1. Чистая установка без сети позволяет создать заказ с двумя товарами; после принудительного завершения приложения все поля и группа сохранены.
2. Заказ с пустой закупочной ценой сохраняется как неполный расчёт, без ложной окончательной прибыли. Пустое значение не равно 0.
3. Позиция 2 × 100 CNY при курсе 13,25 и доставке 350 ₽ даёт себестоимость 3 000 ₽. Продажа 5 000 ₽ даёт предварительную прибыль 2 000 ₽ при подтверждённой полноте затрат.
4. 3 × 0,335 CNY × 10 RUB/CNY дают 10,05 ₽ за строку, а не 10,20 ₽. Суммирование округлённых строк детерминированно.
5. После завершения формирования №1 новые заказы попадают в №2, №1 остаётся на расчёте. Повторная команда не создаёт №3. Сбой посередине транзакции не оставляет две активные группы/заказы без группы.
6. Частичная оплата не превращается в полностью оплаченную автоматически; неверный ввод показывает ошибку и не теряется.
7. Поиск артикула находит ранее использованный товар. Повторное сохранение заказа не создаёт второй факт продажи в истории.
8. Расход уровня группы включён в итог один раз; отдельные заказы явно показывают прибыль без его распределения.
9. Экспорт → восстановление в чистом состоянии сохраняют UUID, заказы, строки, группы и суммы. Повреждённый/более новый неподдерживаемый архив оставляет текущую базу неизменной.
10. Миграция схемы не удаляет ранее введённые данные; fallbackToDestructiveMigration запрещён.
11. Двойное нажатие «Сохранить» не создаёт два заказа. Тяжёлые операции не выполняются на UI-потоке, значения не теряются при повороте/возврате.
12. Реальный тест на Xiaomi выполняет Дмитрий. До этого в отчёте писать «собрано/проверено тестами», а не «работа на устройстве подтверждена».

Приёмка будущих переносов: пример 197 000 ₽, частичный зачёт/передача, повтор команды, возврат после сверки, возврат клиенту отдельно от возврата посредника, аванс больше новой группы, смена курса без изменения прошлого снимка, отмена со сторно. Прибыль новой группы не меняется от зачёта старого долга.

## 11. Поставка и репозиторий

Передать APK с версией, SHA-256, исходники с Gradle Wrapper, README, это ТЗ, AGENTS.md, CHANGELOG, схемы Room и тесты. Не требовать Android Studio от пользователя. Результаты сборки/тестов фиксировать фактически. Незавершённая проверка — ограничение, а не успех.

Репозиторий Private. До первого push проверить видимость; публичные forks, Pages и внешняя публикация исходников не нужны. В репозитории только код, документация и синтетические тесты — без реальных заказов, переписок, баз, резервных копий и ключей. Actions, если добавляются, с минимальными разрешениями; Kimi не обязан ими пользоваться. Первый коммит — документация и правила; реализация отдельным этапом после этого задания.

Для последующего объединения: экспорт версии данных и UUID; явное сопоставление идентификаторов при импорте; финансы закупок отдельно от восстанавливаемого кэша почты. Нельзя заменять историю финансов повторным импортом писем. Общий Core не должен требовать MAX/IMAP для запуска Orders.
